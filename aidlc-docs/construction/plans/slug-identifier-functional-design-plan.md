# Functional Design Plan — slug-identifier ユニット

## 対象
デッキ公開識別子を Google Meet 形式（小文字英字10文字・3-4-3）のランダム ID に一本化する機能の詳細設計。

## 設計タスク（チェックリスト）
- [x] ドメインエンティティ（`decks` の識別子カラム）の差分定義
- [x] ID 生成アルゴリズム（NanoID 辞書/長さ）の定義
- [x] 正規化ルール（保存＝ハイフン無し10文字、表示＝3-4-3）の定義
- [x] 寛容ルックアップ（ハイフン除去後一致）のルール定義
- [x] 一意性・衝突リトライ（UNIQUE / OCC）のビジネスルール定義
- [x] 既存データ移行（後付け採番＋旧URLリダイレクト）のロジック定義
- [x] エラーハンドリング（生成失敗/未検出/重複）の定義

## 確認事項（要回答）

### Q-A: 新 ID の格納カラム戦略
移行（旧URLリダイレクト維持）が必要なため、旧 `slug`/`short_id` の値を保持する必要があります。

A) **新カラム `public_id` を追加**（正規形10文字 `^[a-z]{10}$`・UNIQUE）。`slug`・`short_id` は旧URLリダイレクト用に当面保持（将来削除可）。→ 安全・移行が素直。【推奨】
B) **`slug` カラムを再利用**（中身を正規形10文字に置換）し、旧URL用に `legacy_slug`/`legacy_short_id` を別途追加。→ カラム名は流用するが結局レガシー保持カラムが要る。
C) その他

[Answer]: B（`slug` カラムを再利用＝正規形10文字に置換。旧値保持は `legacy_slug` を新設。`short_id` は既存値がそのまま旧ショートIDなので流用＝`legacy_short_id` は新設しない）

### Q-B: `/s/{code}`（ショートURL）ルートの今後
主URL が10文字と十分短くなるため、専用ショートURLの新規発行は不要になります。

A) **レガシー専用に縮退**: `/s/{old-short-id}` は既存デッキの旧URLリダイレクトのためだけに残す（新規発行はしない）。→【推奨】
B) **新IDでも `/s/{public-id}` を維持**: 短縮共有エンドポイントを今後も提供する。
C) 廃止（旧 short_id リダイレクトも提供しない）。※Q3「移行必要」と整合させるなら非推奨。

[Answer]: A（レガシー専用に縮退。新規デッキに short_id は振らない）

### Q-C: 移行スクリプトの実行形態
A) **既存の `apply-schema.ts` と同様の Node/TS スクリプト**として `src/` 配下に追加し、手動実行する。→【推奨】
B) その他（CDK カスタムリソース等）

[Answer]: A（`apply-schema.ts` 同様の TS スクリプトを `src/` に追加し手動実行）

---

## 設計確定メモ
- `short_id`（既存カラム）が既に旧ショートIDを保持しているため、`legacy_short_id` は新設せず `short_id` を旧URLリダイレクト用に流用する。新規追加カラムは `legacy_slug` のみ。
