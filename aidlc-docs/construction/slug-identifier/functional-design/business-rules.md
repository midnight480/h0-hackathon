# ビジネスルール — slug-identifier

## BR-1: ID 形式
- 公開IDは**小文字英字 a–z のみ・10文字**。数字・大文字・記号を含まない。
- 表示は `3-4-3` のハイフン区切り（`abc-defg-hij`）。
- 採番は **NanoID**（辞書 `abcdefghijklmnopqrstuvwxyz`、長さ 10）。

## BR-2: 採番場所とタイミング
- 採番は frontend の server action `createDeckRecord`（`frontend/app/actions/upload.ts`）で、デッキINSERT時に行う。
- ユーザーによるカスタム入力は受け付けない（入力フィールドを設けない）。

## BR-3: 正規化（保存・検索）
- **保存**: 正規形（ハイフン無し10文字）を `slug` に格納する。
- **検索**: 入力値は `normalize()`（ハイフン除去＋小文字化）してから `slug` と完全一致で照合する。
- 結果として、`abc-defg-hij` でも `abcdefghij` でも同一デッキへ解決する（寛容ルックアップ）。

## BR-4: 一意性と衝突リトライ
- `slug` の UNIQUE 制約を一意性の最終防衛線とする。
- INSERT が UNIQUE 違反になった場合、**新しい ID を再生成して再試行**する（最大 N 回、推奨 N=5）。
- Aurora DSQL は OCC のため、**OCC コンフリクト（SQLSTATE `40001` / DSQL `OC001` 等）も catch して再試行**する。
- リトライ上限到達時は明示的なエラーを返す（暗黙の失敗にしない）。

## BR-5: ルーティング解決順序（閲覧時）
主URL `/@{user}/{idOrSlug}` のアクセスで、`idOrSlug` を以下の順に解決する。
1. `normalize(idOrSlug)` が `^[a-z]{10}$` を満たすなら、`slug = normalized` で検索。ヒットすれば**そのまま表示**。
2. 1で未ヒット、または形式が正規IDでない場合、`legacy_slug = idOrSlug`（原文）で検索。ヒットすれば**新URL `/@{user}/{format(slug)}` へ 301 リダイレクト**。
3. いずれも未ヒットなら 404。

## BR-6: ショートURL（レガシー専用）
- `/s/{code}` は `short_id = code` で検索し、ヒットすれば**新URL `/@{user_id}/{format(slug)}` へ 301 リダイレクト**する。
- 新規デッキには `short_id` を採番しない（`/s/` は既存デッキの旧リンク救済のみ）。

## BR-7: 既存データ移行（後付け採番）
- 対象は `slug` がまだ正規形（`^[a-z]{10}$`）でないデッキ。
- 各デッキについて: 現 `slug` を `legacy_slug` に退避 → 新IDを採番 → `slug` を新IDで更新。
- **冪等性**: 既に `slug` が `^[a-z]{10}$` のデッキはスキップ（再実行で二重採番しない）。
- 移行中も UNIQUE/OCC を尊重し、衝突時はBR-4と同様に再生成リトライ。

## BR-8: 可視性ルール（既存維持）
- `is_public = false` のデッキは所有者のみアクセス可（既存の所有者チェックを維持）。
- ID のランダム性により、非公開デッキのURL推測・列挙を困難にする。

## BR-9: エラーハンドリング
| シナリオ | 振る舞い |
|---|---|
| ID生成リトライ上限到達 | 採番失敗エラーを返し、デッキ作成を中断 |
| 主URLで未検出 | BR-5 の順に解決。最終的に未検出なら 404 |
| 旧URL→新URL解決 | 301（恒久リダイレクト） |
| 移行中の衝突 | 再生成リトライ。上限到達でそのデッキをスキップ＆ログ記録（全体は継続） |
