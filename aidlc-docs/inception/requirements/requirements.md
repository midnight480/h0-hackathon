# 要件定義書 — 公開識別子（Google Meet 形式 slug）の刷新

## インテント分析サマリ

| 項目 | 内容 |
|---|---|
| **ユーザー要求** | アップロードされたデッキの公開URL識別子を、Google Meet 形式（小文字英字 3-4-3 ハイフン区切り・10文字）のランダム ID に刷新する。ユーザーによるカスタム slug 入力は採用しない。 |
| **リクエスト種別** | Enhancement（既存機能の改善） |
| **スコープ** | Single Component（frontend のアップロード処理 + DSQL スキーマ + 閲覧ルーティング） |
| **複雑度** | Moderate（既存の2識別子の統廃合・既存データ移行・ルーティング変更を含む） |
| **対象プロジェクト** | Hiravi（スライド共有・自動翻訳プラットフォーム / Brownfield） |

### 背景（現状の課題）
現状、デッキには公開識別子が **2 本**存在する。
- `slug`（TEXT UNIQUE）= `タイトルkebab + UUID先頭8桁`、主URL `/@{user}/{slug}` で使用（`frontend/app/actions/upload.ts:60-68`）
- `short_id`（VARCHAR(8) hex）= ランダム8桁、ショートURL `/s/{short_id}` で使用しリダイレクト（`frontend/app/s/[code]/route.ts`）

タイトルベース slug は推測可能・タイトル変更時の不整合・冗長などの難があり、識別子が2系統あることで運用も複雑。これを**ランダムな短い ID 1 系統**へ統一する。

---

## 機能要件（Functional Requirements）

### FR-1: Meet 形式ランダム ID の生成
- デッキ作成時に、**小文字英字 a–z のみ・10文字**のランダム ID を生成する。
- 表示形式は `3-4-3` のハイフン区切り（例: `abc-defg-hij`）。数字・大文字は使用しない。
- 生成には NanoID（辞書 `abcdefghijklmnopqrstuvwxyz`・長さ 10）を用いる。
- 採番場所は現状どおり **frontend の server action（`frontend/app/actions/upload.ts`）**。

### FR-2: 識別子の一本化
- 主URL を `/@{user}/{meet-id}` とする（ユーザー名前空間 `/@{user}/` は維持、デッキ識別子部分を Meet 形式 ID に置換）。
- 主URL から**タイトル文字列は除去**する（タイトル接頭辞を付けない）。
- 既存の `short_id`（8桁hex ショートURL）は**廃止**し、Meet 形式 ID に統合する。

### FR-3: 保存（正規化）とルックアップ（寛容な一致）
- DB には**ハイフン無しの正規形（10文字 `abcdefghij`）**を canonical 値として保存する。
- 表示時に `3-4-3` へ整形する。
- ルックアップ時は、入力 ID から**ハイフンを除去してから一致検索**する（ハイフン有無のどちらでも同一デッキへ解決＝コピペ事故に強い）。

### FR-4: 一意性と衝突処理
- 当該カラムに **UNIQUE 制約**を付与する。
- 衝突時（UNIQUE 違反）は**再生成してリトライ**する。
- Aurora DSQL は OCC（楽観的同時実行制御）のため、UNIQUE 違反と **OCC コンフリクト（`OC001` 等）の双方を catch して再試行**できるようにする。

### FR-5: 既存データの移行
- 既存デッキに対し、Meet 形式 ID を**後付けで採番**する（バックフィル）。
- 旧URL（`/@{user}/{title-slug}`、`/s/{short_id}`）でのアクセスは、**新URL（`/@{user}/{meet-id}`）へリダイレクト**して維持する。
- 移行はべき等（再実行しても既採番分を二重採番しない）に実装する。

## 非機能要件（Non-Functional Requirements）

### NFR-1: 衝突確率（容量計画）
- 空間サイズは `26^10 ≈ 1.4×10^14`。誕生日問題に基づき、発行数が中規模（数百万件）でも実用上の衝突確率は無視できる。最終防衛線として UNIQUE 制約＋リトライ（FR-4）を必須とする。

### NFR-2: URL 共有性 / ユーザビリティ
- コピペ共有が主前提。数字を排した英字のみとし、見間違い（`0/O`, `1/l`）を回避。
- ハイフン有無の寛容なルックアップ（FR-3）により、共有時の崩れに耐える。

### NFR-3: セキュリティ / 推測耐性
- ランダム ID により URL 列挙・推測による非公開デッキの探索を困難にする。
- 既存の公開/非公開判定（`is_public`、所有者チェック）は維持する。

### NFR-4: DSQL 整合性
- ランダム ID によりキーが分散するため、同時 INSERT のキー衝突は構造的にほぼ発生しない。
- リトライ処理は冪等で、リトライ可能エラー（OCC コンフリクト・UNIQUE 違反）と非リトライエラーを区別する。

### NFR-5: 後方互換性
- 旧URL からのリダイレクト（FR-5）により、既に共有された旧リンクを壊さない。

## スコープ外（Out of Scope）
- ユーザーによるカスタム slug 入力機能（**不採用**で確定）。
- 多言語スラッグ・SEO 最適化のためのタイトル付きURL。
- ID 形式のユーザー設定/管理画面。

---

## 主要設計上の決定（確認済み）
| 論点 | 決定 |
|---|---|
| 適用範囲 | 主URL を Meet 形式に一本化（`short_id` 廃止） |
| タイトル表示 | ID のみ（タイトル接頭辞なし） |
| 既存データ | 後付け採番＋旧URLリダイレクト維持 |
| 採番場所 | frontend `upload.ts` |
| 形式 | 小文字英字 a–z・10文字・3-4-3 ハイフン区切り |
| 保存/検索 | ハイフン無し正規形を保存、ハイフン除去で寛容に検索 |
| 生成/一意性 | NanoID + UNIQUE + 衝突リトライ + DSQL OCC 対応 |

## 影響範囲（既存コード）
- `src/schema/schema.sql`（`decks` テーブル: `slug`/`short_id` カラム定義、UNIQUE 制約、インデックス）
- `frontend/app/actions/upload.ts`（`toSlug` / `generateShortId` / `createDeckRecord` の置き換え）
- `frontend/app/[user]/[slug]/page.tsx`（ルックアップを Meet 形式 ID／寛容一致へ）
- `frontend/app/s/[code]/route.ts`（ショートURL の扱い／リダイレクトの再設計 or 廃止）
- 既存デッキ向け移行スクリプト（新規）

---

## 主要要件サマリ
- デッキの公開識別子を **Google Meet 形式（小文字英字10文字・3-4-3 ハイフン）のランダム ID** に一本化する。
- カスタム入力なし。NanoID 生成 + UNIQUE + 衝突リトライ + DSQL OCC 対応。
- 保存はハイフン無し正規形、検索はハイフン除去で寛容に解決。
- 既存デッキは後付け採番し、旧URLはリダイレクトで維持する。
